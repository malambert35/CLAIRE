# Preservation and disaster recovery plan

Not an implemented backup subsystem. Do not claim restore readiness until a clean-host exercise succeeds.

Authoritative future layout:

```text
families/<family UUID>/shared/memories/<memory UUID>/revisions/<revision>/
families/<family UUID>/users/<user UUID>/private/memories/<memory UUID>/revisions/<revision>/
```

Each immutable revision contains UTF-8 `content.md` and `metadata.json`. HEAD.json is the atomic archive commit point. Event dates, recording times, contributors, sources and disputes remain separate. The API writes the archive before committing its operational catalogue. If a process fails between those steps, reads fail closed with 503 rather than exposing a stale sharing policy. Original testimony is never regenerated by a model.

## Interrupted memory write

Stop web and worker processes. Keep an untouched copy of the archive and database. Using migration/owner credentials and the same `CLAIRE_DATA_DIR`, run:

```sh
uv run python -m claire.archive_admin MEMORY_UUID
```

This validates committed revisions and updates only the catalogue to the HEAD revision. Original owner/family must exist; recovery cannot transfer ownership or roll back a newer catalogue. Runtime credentials should not run this operator procedure. Restart and test owner access plus denial for a revoked family reader. An interrupted archive write before HEAD may leave `.write-lock` or an uncommitted revision directory; preserve these for diagnosis and do not blindly remove locks while any writer is running. Fully automatic crash recovery is still pending.

## Foundation recovery

Stop app and worker writes. Back up PostgreSQL with `pg_dump --format=custom`, preserve deployment version, archive volume, and role inventory. Store secrets separately in an encrypted password manager or recovery package. Restore on an isolated host using the same PostgreSQL major version, restore roles and database, verify migrations and login, then reconnect the proxy. Keep original backups untouched. These instructions require a recorded Docker restore exercise before production.

## Mandatory future exercise

1. Create two fictional families with private/shared memories, source files and conflicting accounts.
2. Export checksummed Markdown/JSON, original sources, ACL manifest and schema documents.
3. Verify the package offline, inspect it without CLAIRE, and scan for plaintext secrets.
4. Restore database-consistent files and database into a clean Linux host with no original volumes.
5. Rebuild search with a different embedding model while retaining old indexes until verified.
6. Switch local model provider; compare archive checksums before/after.
7. Test API/search/chat/graph/MCP denial across accounts and revoked grants.
8. Have a designated successor perform recovery from the portable guide alone.
9. Record recovery time, missing keys/dependencies, checksum errors and remediation.

Legacy packages must include architecture, versioned schema, deployment templates, dependency manifest, backup inventory, import/restore instructions and key-recovery requirements. Never include plaintext credentials. Designated successors may verify backup availability without receiving private content. Require explicit authorization and, where configured, multiple trusted participants; never release archives solely because of inactivity.

Use 3-2-1 storage with at least one offline/immutable copy and restic encryption under family-controlled keys. Full server loss, corruption, accidental deletion, replacement hardware and migration away from Unraid all need independent verification. RAID/parity does not replace backup.
